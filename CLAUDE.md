# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Nuxt 4 starter kit: shadcn-vue on Tailwind CSS 4, i18n (ru/en), Pinia,
vee-validate + zod, `@nuxtjs/seo`, Vitest and Playwright. TypeScript throughout,
Nuxt 4 directory layout with the `app/` folder.

## Commands

```bash
npm run dev          # dev server on http://localhost:3000
npm run build        # production build
npm run preview      # preview the production build

npm run lint         # eslint
npm run lint:fix     # eslint --fix
npm run format       # prettier
npm run typecheck    # vue-tsc via `nuxt typecheck`
npm run design:check # tailwind.css tokens match DESIGN.md

npm run test:unit    # vitest, single run
npm run test:e2e     # playwright
```

Before declaring work done, run `npm run lint`, `npm run typecheck`,
`npm run design:check` and `npm run test:unit` — CI runs all four plus the
build and e2e.

## Architecture

### Directories

- `app/` — application source (Nuxt 4 `srcDir`; `~` and `@` both point here)
  - `app/components/ui/` — shadcn-vue components, **generated by the CLI**
  - `app/composables/`, `app/stores/`, `app/lib/`, `app/utils/`, `app/plugins/`
  - `app/assets/css/tailwind.css` — Tailwind 4 entry and theme tokens
- `i18n/locales/` — `en.ts`, `ru.ts`
- `server/` — Nitro routes
- `test/unit/` — Vitest, `test/e2e/` — Playwright

`server/` must not import from `app/` — they build for different runtimes. Put
shared code in a top-level `shared/` directory.

### Tailwind CSS 4

There is no `tailwind.config.ts`. Tailwind is wired through the
`@tailwindcss/vite` plugin in `nuxt.config.ts`, and the theme lives in
`app/assets/css/tailwind.css`: OKLCH variables under `:root` / `.dark`, mapped
to utilities in `@theme inline`.

Utilities removed in v4 (`max-w-screen-*`, `flex-shrink-*`, `*-opacity-*`) will
not error — they simply produce no CSS. Watch for them when porting snippets.

### shadcn-vue

Add components with `npx shadcn-vue@latest add <name>`; they land in
`app/components/ui/` and are auto-imported. That directory is excluded from
eslint — change components through the CLI, not by hand.

If the CLI cannot reach the registry, fetch the item directly from
`https://shadcn-vue.com/r/styles/new-york-v4/<name>.json` and rewrite the
`@/lib/utils` / `@/registry/...` imports to `~/`.

### Theming

`@nuxtjs/color-mode` owns the theme: it puts the `dark` class on `<html>` and
injects the anti-FOUC script. Toggle by assigning `colorMode.preference` —
`colorMode.value` is read-only. Do not add manual class handling in layouts.

Note that `useColorMode` also exists in VueUse; the auto-import resolves to
`@nuxtjs/color-mode`, which has a different API.

### Design system: DESIGN.md is the source of truth

`DESIGN.md` in the repo root owns the design of the project. The `:root` /
`.dark` blocks in `app/assets/css/tailwind.css` are **derived** from it.

When the user edits `DESIGN.md` and asks to apply it:

1. Update the token blocks in `app/assets/css/tailwind.css` to match exactly.
2. Apply the prose rules — typography goes into `@theme` as `--font-*`,
   component rules into the components themselves.
3. Run `npm run design:check`. It fails on any mismatch in either direction,
   including a token present in CSS but undocumented in `DESIGN.md`. CI runs it.

Never edit tokens in the CSS directly — that inverts the contract and the check
will fail. Change `DESIGN.md`, then propagate.

Component-level deviations from stock shadcn-vue must be recorded in the
"Отклонения от стоковых компонентов" section of `DESIGN.md`, otherwise the next
`shadcn-vue add` silently reverts them.

### Configuration

Defaults live in `runtimeConfig` in `nuxt.config.ts` and are overridden at
runtime by `NUXT_*` / `NUXT_PUBLIC_*` variables — no rebuild needed. Do not
reintroduce a separate per-environment config module; use `.env` files and
`nuxt build --dotenv .env.<env>`.

### Testing

Vitest runs with `environment: 'nuxt'` via `defineVitestConfig`, so
auto-imports, `#app` and `mockNuxtImport` work inside tests. `test/setup.ts`
recreates Pinia before each test.

E2E targets `data-testid`, never UI text (it is translated). Interactions that
depend on hydration must be written idempotently and wrapped in
`expect(...).toPass()` — the SSR markup is clickable before Vue attaches
handlers.

## Deliberately absent

These were considered and left out on purpose. Do not add them speculatively —
add one only when a concrete feature needs it.

- **Data fetching layer.** Use Nuxt's `useAsyncData` / `useFetch`. TanStack
  vue-query was removed: nothing used it, it cost ~8 kB gzip, and `useQuery`
  renders nothing during SSR unless every call site remembers
  `await suspense()`. Reach for it only in mutation-heavy, app-like screens
  (invalidation graphs, optimistic updates, infinite lists) — and prefer
  scoping it to a client-rendered section via
  `routeRules: { '/admin/**': { ssr: false } }`, where its SSR caveat is moot.
- **Tables.** When one is needed: `@tanstack/vue-table` v9, following the
  shadcn-vue data-table guide.
- **Long lists.** `@tanstack/vue-virtual`.
- **TanStack Store / Router / Start.** Pinia already covers the first; the
  other two replace Nuxt rather than complement it.
- **TanStack Form.** It is schema-agnostic (Standard Schema) and would allow
  zod 4, but shadcn-vue's form components are built on vee-validate — swapping
  loses `<FormField>`. Wait for vee-validate 5 instead.

## Constraints

- **zod stays on 3.x.** `@vee-validate/zod` peer-requires zod 3. Move to zod 4
  only together with vee-validate 5, which drops `toTypedSchema` in favour of
  Standard Schema.
- `package-lock.json` is committed — `npm ci` in CI and Docker depends on it.
- Do not add `legacy-peer-deps`; it previously masked the zod conflict above.
- `overrides` in `package.json` pin `sharp` and `esbuild` to patched versions;
  drop an entry only once the upstream dependency ships the fix.
